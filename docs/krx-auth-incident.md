# KRX 반복 로그인 잠금 조사 (2026-11-04)

## 확인한 사실

- 워크플로의 비밀번호 입력은 모두 `secrets.KRX_PW`이며, 저장소에 예전 비밀번호 문자열이나 인증 파일을 저장하는 별도 경로는 발견하지 못했다. 값 자체는 열람하지 않았다.
- GitHub의 Repository Secret은 워크플로가 대기열에 들어갈 때 읽는다. 사용자가 Secret을 바꿔도 이미 대기/실행 중인 작업은 갱신 전 값을 계속 사용할 수 있다. 따라서 비밀번호를 바꾸기 전에 실행 중 작업뿐 아니라 대기 작업도 종료해야 한다.
- pykrx 1.2.9 `KRXSession.is_valid`는 1시간 만료에 300초 버퍼를 적용하므로 약 55분 후 자동 갱신한다. `get_auth_session`은 갱신 실패 후에도 다음 요청에서 다시 로그인할 수 있다.
- 2026-11-02 성공한 ETF 실행의 13:51:53 KST 로그에 세션 만료 및 재로그인 성공 기록이 있다. 당시 실패하거나 오래된 비밀번호가 전송됐다는 증거는 아니다.
- 최초 수집 시작만 검사하던 기존 차단은 이 중간 갱신 경로를 검사하지 않았다.
- 여러 워크플로와 단계가 각각 새 프로세스에서 인증하므로 실패 횟수가 누적될 수 있었다.

## 수정

- 실제 KRX 로그인 HTTP 요청 경계에서 실패를 즉시 기록하고 같은 프로세스의 후속 KRX 요청을 전송 전에 거부한다. 호출자가 예외를 잡아도 네트워크 재시도를 하지 않는다.
- 로그인 응답 미확인/네트워크 타임아웃도 재전송하지 않는다.
- CD011 중복 세션 해제는 한 번만 허용하며 성공 CD001을 확인한다.
- 실패 당시 단계(initial_login/session_refresh)와 요청 횟수만 기록한다. ID, 비밀번호, 응답 원문, 쿠키, 비밀번호 해시는 기록하지 않는다.
- 기존 공유 인증 차단을 유지하고, 인증 복구 워크플로는 코드 push로 실행하지 않도록 수동 전용으로 변경했다.
- 수동 복구에서는 기존 KRX 수집 작업의 대기/실행 종료를 확인한 다음 로그인한다. 종료를 확인하지 못하면 인증을 시도하지 않는다. 오래된 Secret으로 대기하던 작업이 복구 후 다시 실행되는 경로를 차단한다.
- 이번 수정에서는 KRX에 실제 로그인하지 않았다. 모의 전송 횟수 검증으로 차단 동작을 확인했다.

## 복구 순서

진행/대기 중인 수집 작업 확인 및 종료 → 필요한 경우 KRX 계정 잠금 해제 → GitHub Secret ID/PW 갱신 → 수동 인증 확인 1회. 실패하면 중단하며 연속 재실행하지 않는다.

과거 잘못된 비밀번호가 어떤 장치에서 전달됐는지, 다른 프로그램이 같은 계정을 사용했는지는 보존 로그만으로 확정할 수 없다. CD007 하나만으로 저장된 Secret 값이 잘못됐다고 단정하지 않는다.
